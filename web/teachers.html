For teachers

dewsharp is a set of C# lessons for two QQI Level 5 modules: Programming and Design Principles (5N2927) and Fundamentals of Object-Oriented Programming (5N0541). It is the C# sibling of dewlab, which teaches the same way in Python.

What it is

Each lesson is a web page with some reading and small C# programs, called cells. A learner changes a cell and runs it, and the output appears under it. Pages ask for a guess before some runs, give hints after a learner has tried, and can compare a learner's code with a solution. They never say right or wrong, and they give no marks.

Each course has a practice page for most lessons, and a notebook where learners write their own C#. How the pages work is the learners' guide, and it is short enough to read in class.

What runs where

  • Everything runs in the learner's browser. The C# compiler (Roslyn) and .NET 10 run inside the page, on the learner's own device. There is no server that runs code.
  • Nothing is sent anywhere. The code, the output, the guesses and the saved work stay in that browser, on that device. The site does not collect or store anything about learners, and there are no accounts.
  • The first visit downloads about 15 MB. The browser keeps a copy, so later pages start in a few seconds. An update to the site can mean downloading part of it again. On a shared network, ask learners to open one lesson before the first class.
  • Browsers. The newest Chrome, Edge, Firefox or Safari. Check this device tests a browser in about half a minute and says what to try if a part does not work. It is worth running on your lab's computers once.

What the pages can do, and what they cannot

The pages compile and run ordinary C# 14 console programs, with the same settings as a new Visual Studio console project, except that nullable reference types are off. They can:

  • read what the learner types with Console.ReadLine(), as a real console does;
  • use Console.Clear(), colours and Console.ReadKey(), so console menus work;
  • show compiler messages in Visual Studio's format, Program.cs(3,19): error CS0103: …, and exceptions with the line they happened on;
  • stop a program that runs too long, and let the learner stop it at any time;
  • show money and dates as they are written in Ireland (€12.50, 03/09/2026).

They cannot read or write files, use the network, start threads, open a window (Windows Forms, WPF), stop at a breakpoint and run code one line at a time, complete a name as you type, or hold a solution with several projects. A lesson that needs any of these says so, and sends the learner to Visual Studio with steps.

Cells on a page share code by five rules, the rules of the road. In short: each Run is a new program; classes carry down to the cells below; variables stay in their cell.

How learners keep and hand in their work

  • Saved work stays in the browser, on that device, as the learner types. It does not follow a learner to another computer. If a lesson changes after a learner saved work on it, the page says so, and keeps their code.
  • Lab computers that clear browser data at logout also clear saved work. Check whether yours do. If they do, learners press Export my work before they log out: it saves one file with all their work on every lesson and in every notebook. Import my work brings it back on any computer. A file from an older session never replaces newer work.
  • A notebook can be exported on its own as a file (Export this notebook), which a learner can hand in or share.
  • A Visual Studio project. Download project on any program cell saves a ZIP with a Visual Studio solution: the program, one file for each class cell above it, and a project file with the page's settings. It builds and prints the same output in Visual Studio. This is the usual way to hand in a program, and a good way to keep one.
  • Nothing is submitted from the page. Learners hand in work the way your college does, usually the Visual Studio project, zipped, with the evidence the module descriptor asks for (pseudocode or a flowchart, test data and results, screenshots).

Which parts of the modules the pages cover

Programming and Design Principles (5N2927)

The pages cover types and their sizes, input with prompts, operators, selection, the three kinds of loop, methods with parameters and return values, lists and arrays, searching and sorting, error trapping with TryParse, try and catch, and reading compiler messages. A lesson meets each skill in a cell, then in a task.

In Visual Studio: the debugger (breakpoints and stepping), running a program outside the page, a program in several files, and the team project, which is one Visual Studio project with a file for each member of the team.

Fundamentals of Object-Oriented Programming (5N0541)

The pages cover classes and objects, constructors and overloading, access modifiers and encapsulation, inheritance, virtual and override, interfaces, objects inside objects, testing a class, documentation comments, a console front end, and namespaces. A learner builds one world, a class at a time, over the course.

In Visual Studio: the IDE itself (IntelliSense, the Error List, going to a definition), the debugger, a class library, a test project, a Windows Forms front end (this needs Windows), publishing a program for someone to run, and the whole solution for the third skills demonstration.

Each course page lists its lessons in order. Each lesson lists the learning outcomes it covers at its foot.

Two settings that differ from a new Visual Studio project

  • Top-level statements. The pages write programs without class Program and static void Main. Visual Studio's Console App template has a box, "Do not use top-level statements". Leave it clear, to match the pages. One FOOP page shows the classic Main, because older books use it.
  • Nullable reference types are off. A project a learner makes from Visual Studio's own template has them on, and shows warnings (numbers in the CS86xx range) that the page did not. They are warnings, not errors. A project downloaded from a page has them off.
